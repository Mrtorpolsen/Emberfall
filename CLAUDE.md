# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Emberfall is a 2D tower defense game (Unity **6000.3.9f1**, URP, C#), targeting Android (Google Play Games login, Unity Leaderboards). Development happens on Windows; this repo is accessed from WSL at `/mnt/c/...`.

## Building and testing

There is no CLI build script — builds and play-testing happen in the Unity Editor. Always start Play mode from `Assets/Scenes/Bootstrap.unity`; other scenes depend on singletons it creates.

Tests are NUnit **EditMode** tests in `Assets/Scripts/Tests/Editor/` (compiled into the default `Assembly-CSharp-Editor`; the project has no custom `.asmdef`s). Run them via Window → General → Test Runner, or headless from Windows (the editor must not already have the project open):

```
"C:\Program Files\Unity\Hub\Editor\6000.3.9f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults results.xml [-testFilter WaveGeneratorTests]
```

Some tests load real ScriptableObject assets through `AssetDatabase` (e.g. `WaveGeneratorTests` loads every `SpawnDefinition`), so changing data assets can break tests.

## Repo conventions

- `.cs` files use CRLF; Unity YAML (`.unity`, `.prefab`, `.asset`, `.meta`) uses LF (see `.gitattributes`). Preserve line endings when editing.
- Every asset has a `.meta` file holding its GUID; scenes and prefabs reference scripts by GUID, so don't rename a MonoBehaviour's file without its class.
- `*.csproj`/`*.sln` are generated by Unity and gitignored; don't edit them.
- Scripts are in the global namespace (no `namespace` declarations).

## Unity rules

## Architecture

### Scene flow and global singletons
Build order: `Bootstrap` → `Login` → `UI_Root` (menus) ⇄ `Game`.

- `ServiceInitializer` (Bootstrap scene) creates the persistent services via `GlobalSystem<T>.Create()` (`IdentityService`, `SaveService`, `CurrencyManager`, `UnlockService`), initializes `SpawnDatabase`/`AbilityDatabase`, then loads `Login`.
- `GlobalSystem<T>` (`Core/GlobalSystem.cs`) is the DontDestroyOnLoad singleton base. Many other managers (`UnitStatsManager`, `UIScreenRouter`, `SpawnDatabase`, `GameManager`, …) hand-roll the same `Instance` + `Awake` pattern instead.
- `Bootstrapper` (UI_Root) runs after login: loads the save for the authenticated player, preloads addressables, initializes `UnitStatsManager` and `TutorialFlow`, then routes to `MainMenu`.

### Menu UI (UI Toolkit)
Menus are UI Toolkit (UXML/USS under `Assets/UI Toolkit/`), not uGUI. `UIScreenRouter` swaps screens inside the `ContentContainer` element of UI_Root. Each screen is registered in `UIScreenRouter.Start()` as a triple of interfaces from `Menu/Interfaces/MenuInterfaces.cs`:
- `IUIScreenView` — queries/builds elements (`InitializeAsync`)
- `IUIScreenController` (optional) — screen-scoped logic
- `IUIScreenEvents` — binds callbacks; must unregister in `Cleanup()`

Init order is View → Controller → Events; on swap, Events and Controller are cleaned up. Adding a screen = create the three classes under `Scripts/Menu/<Feature>/`, a UXML, a `VisualTreeAsset` field on `UIScreenRouter`, and a `RegisterScreen` call. Long-lived per-feature state lives in `*Service` classes (`TalentService`, `ResearchService`, `LoadoutService`, `LeaderboardService`).

The in-game HUD (`Game/UI/UIManager`, `ActionButton`) is separate from the menu router.

### Persistence
`SaveService` writes a single JSON file (Newtonsoft) per player ID. `SaveGame` (`Shared/Persistence/SaveGame.cs`) is the root; `CurrentSaveVersion.CURRENT_SAVE_VERSION` gates migration. **When changing the save shape**: bump the version, keep the old shape as a `SaveGameN` class (legacy types live under `SaveMigration/vN/`), and add a `MigrateNToM` case in `SaveService.Migrate`. Corrupt saves are copied aside rather than overwritten.

### Data definitions
- ScriptableObjects under `Assets/Resources/ScriptableObjects/` define units (`UnitStatsDefinition`), spawnable entries (`SpawnDefinition`), generals/bosses (`GeneralDefinition`), abilities (`AbilityDefinition` + `AbilityAction` assets), and targeting.
- Talent and research trees are JSON (`Assets/Resources_moved/Data/Talents.json`, `Research.json`) loaded through **Addressables** by key (`"Talents"`, `"Research"`). Icons and many UI assets are also addressable — new addressable assets must be added to a group in `AddressableAssetsData`.

### Unit stats pipeline
All numeric stats are a `StatBlock` (one float per `StatType`; int stats are rounded only on read via `GetInt`). `StatType` is serialized as an int in assets, so only append to it. `UnitStatsDefinition.ToStatBlock()` is the single definition→stats mapping.

Every modifier goes through `StatPipeline`: `base * (1 + sum of Percent) + sum of Flat`, `Set` overrides. Percentages are additive and only scale the base, not flat bonuses.

1. `StatsBootstrapper` reads purchased talents/research from the save and groups their `StatEffect`s (by unit key / research category).
2. `UnitStatsCalculator.ApplyModifiers` converts them (`StatModifier.FromEffect`; JSON Multiply `1.05` = +5% Percent, scaled by stacks) and runs research + talents through the pipeline in one pass, relative to the definition values. Enemy wave scaling (`CalculateEnemyStats`) is applied on top for enemies.
3. `UnitStatsManager` caches the result per unit key in `FinalStatsByUnit`; `SpawnManager` passes it to spawned units via `ApplyFinalStats`.
4. Each unit's `BaseUnitStats` keeps progression → base (+ permanent changes via `BuildBaseStats`, e.g. `TowerUnitStats` tiers multiply the upgraded stats) → current (+ runtime `StatModifier`s from `EffectSystem`, recalculated for dirty stats in `LateUpdate`). Runtime percentages therefore scale the upgraded value. `RuntimeStats` only holds non-numeric values (`unitPrio`, `isTargetable`).

Each unit type has a thin `*BaseStatsComponent : BaseUnitStats` subclass (mostly just `UnitPrio` threat level) in `Units/Components/BaseStats/`; towers derive from `TowerUnitStats`. Behaviour is composed from sibling components (`MovementComponent`, `CombatComponent`, `TargetComponent`/`TargetSelector`, `RangedShooter`, `UnitAbilityComponent`) plus `TargetRegistry` for lookups.

### Match economy
In-match currency and income live in `MatchEconomy` (plain C#, tested), owned by `GameManager.Economy` and ticked while the game runs. Spend with `TrySpend` (checks and subtracts in one call); the HUD (`UIManager`) listens to `CurrencyChanged`/`IncomeChanged` instead of being called. Meta-currency (cinders/embers in the save) is separate: `CurrencyManager`.

### Waves and abilities
- `WaveController` drives a match; `WaveGenerator` builds each `WaveDefinition` from the `SpawnDatabase` using a threat budget (`WaveThreatCalculator`, `WaveRules`, `Difficulty`) and the selected `GeneralDefinition` (boss). It takes an injectable random function for tests.
- Abilities: `AbilityDefinition` → `AbilityAction`s (`Heal`, `StatModification`, `Summon`), triggered via `AbilityTriggerFactory`/`AbilityTrigger` (e.g. cooldown-based), executed by `AbilitySystem` with `AbilityCooldownManager`.

### Tutorial
`TutorialFlow` (persistent) owns menu tutorial steps and flags in `PlayerFlagsState`; `GamePlayTutorialPresenter` handles the in-game tutorial. `GameManager` has an `isTutorial` mode that changes spawning (e.g. the tutorial boss `SirTutorTheThird`) — check tutorial vs. normal paths when touching spawning/waves.
