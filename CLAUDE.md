# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Emberfall is a 2D tower defense game (Unity **6000.6.8f1**, URP, C#), targeting Android (Google Play Games login, Unity Leaderboards). Development happens on Windows; this repo is accessed from WSL at `/mnt/c/...`.

## Building and testing

There is no CLI build script — builds and play-testing happen in the Unity Editor. Always start Play mode from `Assets/Scenes/Bootstrap.unity`; other scenes depend on singletons it creates.

Tests are NUnit **EditMode** tests in `Assets/Scripts/Tests/Editor/` (compiled into the default `Assembly-CSharp-Editor`; the only `.asmdef` is the generated Cloud Code bindings' under `Assets/CloudCode/`). Run them via Window → General → Test Runner, or headless from Windows (the editor must not already have the project open):

```
"C:\Program Files\Unity\Hub\Editor\6000.6.8f1\Editor\Unity.exe" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults results.xml [-testFilter WaveGeneratorTests]
```

Crash reporting is Unity Diagnostics, enabled in the project settings. Debug symbols are set in Build Profiles, not Player Settings, so they aren't committed. Upload each shipped build's symbols as described under "Releasing" in `docs/release-plan.md`. `CrashReportingTester` (on GameManager) only works in development builds: hold the top-left corner to throw an exception, or the top-right corner to force a native crash. The other tools in `Game/Debug` (`ClickDebugger`, `VelocityInspector`, `DrawCircle`) work in the Editor and development builds; in release builds they destroy themselves in `Awake` (runtime `Debug.isDebugBuild` check; the `DEVELOPMENT_BUILD` define is deprecated since Unity 6.6). Wrap new debug components the same way rather than removing them from scenes and prefabs.

Some tests load real ScriptableObject assets through `AssetDatabase` (e.g. `WaveGeneratorTests` loads every `SpawnDefinition`), so changing data assets can break tests.

## Repo conventions

- All text files use LF (`.gitattributes` + `.editorconfig`); keep LF when editing. Unity's "Line Endings For New Scripts" (Project Settings → Editor) is set to Unix.
- Every asset has a `.meta` file holding its GUID; scenes and prefabs reference scripts by GUID, so don't rename a MonoBehaviour's file without its class.
- `*.csproj`/`*.sln` are generated by Unity and gitignored; don't edit them.
- Scripts are in the global namespace (no `namespace` declarations).
- The GPGS plugin (`Assets/GooglePlayGames/`) is patched: `GPGSProjectSettings.Save()` sets `wr.NewLine = "\n"` so `ProjectSettings/GooglePlayGameSettings.txt` (rewritten on every domain reload) stays LF, and `GPGSUpgrader` no longer logs "start"/"done" on every recompile. Re-apply both after upgrading the plugin. External Dependency Manager's verbose logging is off (`ProjectSettings/GvhProjectSettings.xml`).

## Architecture

### Scene flow and global singletons
Build order: `Bootstrap` → `Login` → `UI_Root` (menus) ⇄ `Game`.

- `ServiceInitializer` (Bootstrap scene) creates the persistent services via `GlobalSystem<T>.Create()` (`IdentityService`, `SaveService`, `CurrencyManager`, `UnlockService`), initializes `SpawnDatabase`/`AbilityDatabase`, then loads `Login`.
- `GlobalSystem<T>` (`Core/GlobalSystem.cs`) is the DontDestroyOnLoad singleton base. Many other managers (`UnitStatsManager`, `UIScreenRouter`, `SpawnDatabase`, `GameManager`, …) hand-roll the same `Instance` + `Awake` pattern instead.
- `LoginManager` (Login) initializes Unity Services with `ServicesEnvironment.Current`: UGS environment `development` in the editor and development builds, `production` in release builds (Cloud Save, leaderboards, Cloud Code and Remote Config are per environment, so `development` needs the same leaderboards, scripts and secrets). The Deployment window's environment selection (`ProjectSettings/Packages/com.unity.services.core/Settings.json`, committed as `development`) only picks the deploy target. It signs in through Unity Authentication. A cached session (guest or Google) is restored silently; on first launch the player chooses "Sign in with Play Games" (Google Play Games, Android only; `PlayGamesManager` fetches the server auth code) or "Continue as guest" (anonymous), then sets a name if the account has none (checked by `ProfanityFilter` against `Assets/Data/ProfanityWords.txt`, a TextAsset assigned on `LoginManager`; add `+word` lines there for false positives). If restoring a saved session fails (offline), it plays offline as the last player: `UnityAuthIdentity` caches the player ID in PlayerPrefs and returns it while signed out. After an offline start, `IdentityService.TryReconnectAsync` restores the session mid-session (on opening the leaderboard or account popup, after an offline score, and every 2 minutes); it only uses the saved session token, never a fresh anonymous account, and raises `IdentityService.Reconnected` on success (the score queue is submitted and the top bar refreshed). GPGS only works in device builds.
- `Bootstrapper` (UI_Root) runs after login: loads the save for the authenticated player, preloads addressables, initializes `UnitStatsManager` and `TutorialFlow`, then routes to `MainMenu`.

### Menu UI (UI Toolkit)
Menus are UI Toolkit (UXML/USS under `Assets/UI Toolkit/`), not uGUI. `UIScreenRouter` swaps screens inside the `ContentContainer` element of UI_Root. Each screen is registered in `UIScreenRouter.Start()` as a triple of interfaces from `Menu/Interfaces/MenuInterfaces.cs`:
- `IUIScreenView` — queries/builds elements (`InitializeAsync`)
- `IUIScreenController` (optional) — screen-scoped logic
- `IUIScreenEvents` — binds callbacks; must unregister in `Cleanup()`

Init order is View → Controller → Events; on swap, Events and Controller are cleaned up. Adding a screen = create the three classes under `Scripts/Menu/<Feature>/`, a UXML, a `VisualTreeAsset` field on `UIScreenRouter`, and a `RegisterScreen` call. Long-lived per-feature state lives in `*Service` classes (`TalentService`, `ResearchService`, `LoadoutService`, `LeaderboardService`).

`LeaderboardService.AddScore` never drops a score: it goes into `PendingScoreQueue` (PlayerPrefs, best per player ID and difficulty, plain C# and tested) and is removed only after the server accepts it (or already has a higher one). `SubmitPendingScoresAsync` sends the queue when signed in; `Bootstrapper` calls it after loading the player's scores, and a reconnect does too.

Tapping the username in the top bar opens `AccountPopup` (guests: link Play Games; account deletion via `AccountService`, which first deletes the player's leaderboard scores through the `DeletePlayerScores` Cloud Code script, then restarts the game from Bootstrap by destroying our DontDestroyOnLoad objects). The script's source is `CloudCode/DeletePlayerScores.js`; it's deployed by pasting it into the Unity Dashboard, and it reads a service account key from Secret Manager.

Short player-facing messages (errors, confirmations) go through `Toast.Show(message)`, a drop-down banner built in code; `LoginManager` and `Bootstrapper` attach it to their UIDocument roots. Modal popups with buttons use `PopupManager`.

The in-game HUD (`Game/UI/UIManager`, `ActionButton`) is separate from the menu router. Unit buttons send one unit per tap and keep sending while held (`ActionButton.SetHoldAction`).

Rally points (`GameManager.MeleeRally` and the two ranged rallies) are moved by dragging, not a menu: `RallyDragController` (runs before other input via `DefaultExecutionOrder`) grabs the nearest rally within `grabRadius`, and `GameManager.MoveRally` keeps it inside its boundary trigger (`meleeRallyBoundary`/`rangedRallyBoundary`, the `RallyBoundary` polygon in `Game.unity`) with `ClosestPoint`. While `RallyDragController.IsDragging`, `CameraController` doesn't pan and `ClickTracker` ignores the press. Units re-read their rally's position every frame, so they follow a drag without extra code.

### Persistence
`SaveService` writes a single JSON file (Newtonsoft) per player ID; the JSON ↔ `SaveGame` step (parse, migrate, fill missing sections) is the plain C# `SaveSerializer`, covered by `SaveLoadTests`. Save classes are plain C# without `[Serializable]` (Unity never serializes them); never put `[NonSerialized]` on a save field, since Newtonsoft skips those too. `SaveGame` (`Shared/Persistence/SaveGame.cs`) is the root; `CurrentSaveVersion.CURRENT_SAVE_VERSION` gates migration. **When changing the save shape**: bump the version, keep the old shape as a `SaveGameN` class (legacy types live under `SaveMigration/vN/`), and add a `MigrateNToM` case in `SaveService.Migrate`. Corrupt saves are copied aside rather than overwritten.

Cloud save is in progress (`feat/cloud-save`, design in `docs/cloud-save.md`): progress becomes Cloud Save Protected data written only by the Cloud Code C# module `EmberfallModule`. Its .NET solution is `CloudCode/EmberfallModule/` (`Project/` is the module, `TestProject/` its NUnit tests; targets `net9.0`, outside `Assets/` so Unity doesn't compile it). `Assets/CloudCode/EmberfallModule.ccmr` points at it: deploy from Services → Deployment, then regenerate the bindings from the `.ccmr` Inspector. The generated client wrappers (`Assets/CloudCode/GeneratedModuleBindings/`, e.g. `ProgressModuleBindings`) are overwritten on regeneration, so don't edit them. Module code uses a namespace (`EmberfallModule`); the global-namespace rule is for Unity scripts.

### Data definitions
- ScriptableObjects under `Assets/Data/ScriptableObjects/` define units (`UnitStatsDefinition`), spawnable entries (`SpawnDefinition`), generals/bosses (`GeneralDefinition`), abilities (`AbilityDefinition` + `AbilityAction` assets), and targeting. They're referenced directly (scenes/prefabs), not loaded by path.
- Enemies reuse the player's `SpawnDefinition`s (general rosters), so "enemy" is derived from `GeneralDefinition.unitRoster`/`generalUnit`. Spawns that are never the player's (bosses) are flagged `SpawnDefinition.enemyOnly` and kept out of the loadout by `LoadoutService`. Player units and towers carry `LoadoutDefinition.loadoutDescription`, shown under the stats in the loadout popups; `DataValidationTests` require it on every non-enemy-only spawn. A general's `generalUnit` can be a player unit (Bert → Giant, Feff → Elite Cavalier), so the flag is set by hand, not derived.
- Unlocks aren't saved: `UnlockService` is rebuilt every launch from `unlockedByDefault` definitions (`ServiceInitializer`, permanent, so `Lock` ignores them), purchased unlock talents and completed global-ability research. A talent refund (`TalentService.RefundAllAsync`) re-locks talent unlocks and empties loadout slots in every preset that are no longer unlocked (`LoadoutService.RemoveLockedDefinitions` → `LoadoutPruner`); `Bootstrapper` runs the same cleanup after loading the save.
- Talent and research trees are JSON (`Assets/Addressables/Data/Talents.json`, `Research.json`) loaded through **Addressables** by key (`"Talents"`, `"Research"`). Menu UXML/USS templates live under `Assets/Addressables/UI/`. Icons and many UI assets are also addressable — new addressable assets must be added to a group in `AddressableAssetsData`.
- `Assets/Resources/` only holds what is loaded by path — `Resources.Load` in code or `resource("…")` in UXML/USS: currently `UI/cinder_icon.png`. Everything in `Resources` ships in every build, so don't put referenced assets there, and don't move anything out of it without checking for `resource(` references.

### Unit stats pipeline
All numeric stats are a `StatBlock` (one float per `StatType`; int stats are rounded only on read via `GetInt`). `StatType` is serialized as an int in assets, so only append to it. `UnitStatsDefinition.ToStatBlock()` is the single definition→stats mapping.

Every modifier goes through `StatPipeline`: `base * (1 + sum of Percent) + sum of Flat`, `Set` overrides. Percentages are additive and only scale the base, not flat bonuses.

1. `StatsBootstrapper` reads purchased talents/research from the save and groups their `StatEffect`s (by unit key / research category).
2. `UnitStatsCalculator.ApplyModifiers` converts them (`StatModifier.FromEffect`; JSON Multiply `1.05` = +5% Percent, scaled by stacks) and runs research + talents through the pipeline in one pass, relative to the definition values. Enemy wave scaling (`CalculateEnemyStats`) is applied on top for enemies.
3. `UnitStatsManager` caches the result per unit key in `FinalStatsByUnit`; `SpawnManager` passes it to spawned units via `ApplyFinalStats`.
4. Each unit's `BaseUnitStats` keeps progression → base (+ permanent changes via `BuildBaseStats`, e.g. `TowerUnitStats` tiers multiply the upgraded stats) → current (+ runtime `StatModifier`s from `EffectSystem`, recalculated for dirty stats in `LateUpdate`). Runtime percentages therefore scale the upgraded value. `RuntimeStats` only holds non-numeric values (`unitPrio`, `isTargetable`). Untargetable units (towers, a general while immortal) also take no damage: `BaseUnitStats.TakeDamage` ignores them, so splash attacks don't need their own check.

Each unit type has a thin `*BaseStatsComponent : BaseUnitStats` subclass (mostly just `UnitPrio` threat level) in `Units/Components/BaseStats/`; towers derive from `TowerUnitStats`. Behaviour is composed from sibling components (`MovementComponent`, `CombatComponent`, `TargetComponent`/`TargetSelector`, `RangedShooter`, `UnitAbilityComponent`) plus `TargetRegistry` for lookups.

### Match economy
In-match currency and income live in `MatchEconomy` (plain C#, tested), owned by `GameManager.Economy` and ticked while the game runs. Spend with `TrySpend` (checks and subtracts in one call); the HUD (`UIManager`) listens to `CurrencyChanged`/`IncomeChanged` instead of being called. Meta-currency (cinders/embers in the save) is separate: `CurrencyManager`.

### Waves and abilities
- `WaveController` drives a match; `WaveGenerator` builds each `WaveDefinition` from the `SpawnDatabase` using a threat budget (`WaveThreatCalculator`, `WaveRules`, `Difficulty`) and the selected `GeneralDefinition` (boss). It takes an injectable random function for tests. `WaveRules` hands out generals in shuffled cycles (never the same one twice in a row across a cycle boundary), and `WaveGenerator` spawns a boss whenever the general changes. The tutorial has a single general, so Sir Tutor spawns once. Every 7th wave from 21 is an assassin wave: only assassins (no sappers; a general due that wave arrives with the next one, still sent on its normal last wave), budgeted at `AssassinWaveThreatMultiplier` × the normal threat. `WaveController.totalWaves` (2000 in `Game.unity`) ends the run's spawning when reached; threat scaling that far out hasn't been tuned yet.
- Abilities: `AbilityDefinition` → `AbilityAction`s (`Heal`, `StatModification`, `Summon`), triggered via `AbilityTriggerFactory`/`AbilityTrigger` (e.g. cooldown-based), executed by `AbilitySystem` with `AbilityCooldownManager`.

### Tutorial
`TutorialFlow` (persistent) owns menu tutorial steps and flags in `PlayerFlagsState`; `GamePlayTutorialPresenter` handles the in-game tutorial. `GameManager` has an `isTutorial` mode that changes spawning (e.g. the tutorial boss `SirTutorTheThird`) — check tutorial vs. normal paths when touching spawning/waves.
